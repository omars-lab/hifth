# Going multilingual: what the chrome says, in every language it will say it

> Forward-looking. Read this *before* touching the chrome's vocabulary.
> `docs/decisions/i18n.md` is the shorter retrospective record of what was decided and
> measured; it links here rather than repeating this.

`docs/decisions/loop-*.md` are the record of what a finished loop settled.
`docs/design/` is the other half: the document a reader consults before changing a
feature. This one covers the whole of the chrome's language layer — `apps/web/src/i18n.tsx`,
`apps/web/src/lang.ts`, `apps/web/src/messages/`, `apps/web/src/format.ts`, and the
gates that hold them together.

---

## ① The premise that changed

The old module doc at the top of `i18n.tsx` argued against a library, and it argued
well. Verbatim, the constraint it was defending:

> There are no plurals to negotiate, no dates, no currencies, and exactly two
> languages — the whole of ICU MessageFormat would be dead weight in a bundle
> `gate:budget` measures.

Every clause of that is true, and the conclusion followed from **exactly two languages**.
Two is a special number here: with two, a hand-written table is not a table, it is a pair,
and a pair can be held in one head. `Strings` is an interface, `AR` and `EN` both implement
it, and the compiler catches the one failure that matters — a key added to one and
forgotten in the other. Nothing else was needed, and TypeScript was already paid for.

What changed is the locale count, and the conclusion does not survive it. Three things
break at three:

1. **The pair becomes a matrix.** Today the diff for a new string is two lines. At five
   locales it is five, and four of them are written by someone who cannot read the fifth.
   The interface still catches the *missing* line. It cannot catch the wrong one.
2. **Plural agreement stops being a rounding error** (§②). It is the failure mode that
   reads as slightly-off Arabic, which means nobody files a bug, which means it is
   permanent.
3. **The bundle argument inverts.** The old doc feared a fat ICU runtime, and it was right
   to — `@messageformat/core` in the browser costs **25.2 KB gz** (measured, §③). But the
   dead-weight worry was about a *runtime*. A message **compiler** costs nothing at
   runtime: it runs at build time, and the bundle receives plain functions. The whole
   migration measured **+1.8 KB gzipped** end to end (101.2 → 103.0 KB against a 150 KB
   budget), of which the plural runtime is **+180 bytes** and the rest is the compiled
   catalogs themselves. A runtime ICU library would have added 9.3–25.2 KB *on top of*
   those same catalogs. §③ has the table.

So the old doc's constraint is not being overruled. It is being satisfied more cheaply
than it thought possible, by moving the library from the bundle to the build.

**The one thing the old doc got exactly right, and which this design keeps:** completeness
must be a *build-time* guarantee, not a runtime fallback. See §④.

## ② The plural problem, concretely

Arabic has **six** plural categories. This is not a stylistic claim; it is CLDR, and the
platform will tell you:

```
$ node -e "console.log(new Intl.PluralRules('ar').resolvedOptions().pluralCategories)"
[ 'few', 'many', 'one', 'two', 'zero', 'other' ]
$ node -e "console.log(new Intl.PluralRules('en').resolvedOptions().pluralCategories)"
[ 'one', 'other' ]
```

### The hand-hack that is already in the tree

`AR.distance` in `i18n.tsx` is the one place the current table admits the problem, and it
admits it as a ternary:

```ts
const pages =
  n === 1 ? "صفحة واحدة"
  : n === 2 ? "صفحتان"
  : n <= 10 ? `${digits(n, "ar")} صفحات`
  : `${digits(n, "ar")} صفحة`;
```

That is four of Arabic's six categories, hand-derived, with `n <= 10` standing in for
CLDR's `few`. It is **wrong**, and it is wrong in a way no test in this repo can see.
CLDR's Arabic `few` rule is `n % 100 = 3..10`, not `n <= 10`. So for a page distance of
103–110, 203–210, 303–310, 403–410, 503–510, or 603 the ternary says «١٠٣ صفحة» where
Arabic wants «١٠٣ صفحات».

Page distances run 0…603. **41 of those 603 values — 6.8% — render ungrammatical Arabic
today.** The build vendors three pages, so the largest distance reachable right now is 12
and nobody has ever seen it. Loop 4b vendors the rest and it becomes visible, in a sheet a
hafiz reads, as slightly-wrong Arabic that reads like a typo rather than a bug.

(The same shape is arriving on the RevisionMap branch as `mapHeld`'s «حزب» / «حزبًا»
ternary. It is not in this commit's base, but it is the same defect written a second time,
which is the point: the hand-written scheme *invites* it.)

### The arithmetic of not fixing this

Eight messages in the current table interpolate a count next to a noun that must agree
with it: `pagesVendored`, `railSummary`, `rangeAria`, `legendCountOnPage`, `rootsStats`,
`rootsTruncated`, `rootsOccurrences`, `distance`.

| | forms Arabic needs | forms the table writes |
|---|---|---|
| `distance` | 6 | 4 (a ternary) |
| the other seven | 6 each = 42 | 7 (one invariant form each) |
| **total** | **48** | **11** |

Thirty-seven forms are not missing — that would be a build error — they are *silently
substituted* by whichever single form the author typed. English hides this because English
has two categories and one of them is the bare noun.

Now add locales. Russian and Polish have four categories, Welsh has six, Japanese has one.
Per locale the hand-written scheme costs 134 interface members restated, **and** eight
independent judgements about how many forms this language needs, made by whoever writes
the file and reviewed by whoever can read it — which for a fifth language is nobody on the
team. Five locales is 670 hand-written entries with 40 invented ternaries inside them.

Under ICU the same eight messages are eight `{n, plural, …}` blocks, the category names
are CLDR's, and **`gate:i18n` refuses a locale whose plural block omits a category CLDR
says that locale has** (§④). The judgement moves from the author's memory to the platform.

## ③ The library, and what it was chosen against

### Chosen: ICU MessageFormat, compiled at build time by `@messageformat/parser`

- Catalogs are `apps/web/src/messages/<locale>.json` — flat dotted keys, ICU
  MessageFormat source strings.
- `scripts/build-messages.mjs` parses them with **`@messageformat/parser`** (the reference
  ICU parser; the same one `@messageformat/core` itself uses) and emits **TypeScript** into
  `apps/web/src/messages/*.gen.ts`. Generated files are committed and typechecked.
- The generated code is plain string concatenation plus one 12-line helper
  (`apps/web/src/messages/plural.ts`) over the browser's own **`Intl.PluralRules`**.
- `@messageformat/parser` is a **root devDependency**. It ships **zero bytes**.

The whole path, in order:

```
messages/<id>.json          ICU source, hand-edited, one per locale
  ↓  scripts/messages-compile.mjs   (build time, @messageformat/parser)
messages/catalog.gen.ts     interface Catalog — the shape every locale must fill
messages/<id>.gen.ts        const messages: Catalog = { … }   ← tsc's lock
messages/catalogs.gen.ts    CATALOGS: Record<LocaleId, Catalog>
messages/locales.gen.ts     LOCALE_IDS / LocaleId  →  lang.ts's `Lang`
  ↓  buildStrings(lang, catalog)    (i18n.tsx — written once, run per locale)
Strings                     the shape ~130 call sites already read
  ↓  useT()
components                  unchanged
```

`buildStrings` is the part that keeps the migration cheap and the next language cheaper.
The old file said everything twice; this says the wiring — which formatter, which digits,
which argument — once, so «صفحتان» and "2 pages" cannot be bound differently. It is also
why `useT()`'s shape and every call site are untouched.

### Measured, the way `gate:budget` measures

Each candidate bundled with the app's own Vite, `minify: esbuild`, gzipped. The workload
is the `distance` message — one Arabic six-category plural with two arguments. The floor
is the same message as today's hand-written ternary.

| candidate | raw | **gz** | over the floor |
|---|---:|---:|---:|
| hand-written ternary (the floor, today) | 187 B | **151 B** | — |
| **compiled + `Intl.PluralRules` — chosen** | 449 B | **331 B** | **+180 B** |
| compiled + `@messageformat/runtime` helpers | 593 B | 386 B | +235 B |
| `@lingui/core` runtime | 31,177 B | 9,282 B | +9,131 B |
| `intl-messageformat` (FormatJS) runtime | 63,117 B | 14,164 B | +14,013 B |
| `@messageformat/core` compiling in the browser | 125,578 B | 25,217 B | +25,066 B |

Measured with a scratch Vite build per candidate, deliberately **not** committed — it
depends on five packages this repo does not otherwise install. The numbers above are the
record; re-derive them if you need to challenge them.

**Budget, measured on the real app and not on the probe.**
`scripts/gate-budget.mjs` caps total shipped gzipped JS at 150 KB.

| | total gz | app chunk | headroom |
|---|---:|---:|---:|
| before (hand-written table, `HEAD`) | 101.2 KB | 90.4 KB | 48.8 KB |
| after (this design, whole migration) | **103.0 KB** | 92.2 KB | **47.0 KB** |

**+1.8 KB gz.** The table above says the *machinery* is +180 B; the rest is the compiled
catalogs. That is worth being explicit about, because it is the one number a reader will
otherwise be surprised by: the hand-written table wrote each key twice (once per locale),
and the compiled form writes it three times — once per locale's `.gen.ts`, and once more
in `buildStrings`, which names every key to wire it to a formatter. That third mention is
what buys the single assembler, and the single assembler is what makes a third locale a
JSON file rather than 134 retyped members.

It is also the *last* time the count grows: a fourth locale adds one catalog and no
assembler lines, so the marginal cost of a language is its own words and nothing else.

A runtime library would have spent 9.3–25.2 KB — 19–51% of the headroom — **on top of**
these same catalogs, and would still have needed the assembler.

Reproduce the app figures with `pnpm build && pnpm gate:budget`; reproduce the per-candidate
table with the probe described above.

### Why not the two near-misses

**`@messageformat/runtime`** (+55 B over the chosen design) would let the generator emit
the reference implementation's own output verbatim, which is less of our code to own. It
was rejected for two reasons that are not about bytes: its plural rules are a *vendored
snapshot* of CLDR that goes stale, and this app is offline-first — a build installed on a
phone may run for years without an update, so plural data that the platform refreshes is
strictly better than plural data we froze. And it is a runtime dependency in a GPL app,
with the licensing paperwork that implies, in exchange for 55 bytes.

**`@lingui/core`** is the strongest of the batteries-included options and the one to
revisit if this ever needs runtime-loaded catalogs (it does not; see §⑧). Its macro-based
extraction is genuinely nice. But 9.3 KB gz buys a message runtime we do not need, and its
completeness story is a *runtime* fallback to the source string — which is the exact
failure §④ exists to prevent.

**`typesafe-i18n`** was not measured. It is the closest match in philosophy — compile-time
types, tiny runtime — but it is effectively unmaintained, and a dependency that stops
receiving CLDR updates is the `@messageformat/runtime` objection with no upside.

**Writing our own ICU parser** was rejected on the grounds that ICU MessageFormat's syntax
is finished and someone else has already got it right; the emitter is ours because the
emitter is where the numeral policy (§⑥) lives, and that policy is specific to this app.

## ④ How completeness is enforced

The property being defended, stated as a failure: **a key present in `ar` and missing in
`en` must never render English inside an Arabic sheet, or Arabic inside an English one.**
Today that is a TypeScript error, and the old module doc is right that this is the entire
enforcement story and that it is load-bearing. It stays a TypeScript error. It gains a
second lock and a third.

### Lock 1 — `tsc`: the generated catalog is a typed interface

`scripts/build-messages.mjs` derives `apps/web/src/messages/catalog.gen.ts` from the
**reference locale** (`ar`, because Arabic is the app's native tongue and the wording every
aria snapshot was recorded against). One member per message key, with its exact argument
names and types:

```ts
export interface Catalog {
  readonly mushaf: string;                                    // no arguments → a constant
  readonly pageN: (d: { readonly page: string | number }) => string;
  readonly distancePages: (d: { readonly n: number;           // selects the CLDR category
                                readonly nText: string | number }) => string;  // and prints
  readonly distanceRelative: (d: { readonly dir: "later" | "other";
                                   readonly pages: string | number }) => string;
}
```

Arguments are typed as the **union across locales**, not the reference's alone: English's
`legendCountOnPage` needs an `{n}` to agree with that Arabic's does not. The permissive
direction is deliberate and the strict direction is Lock 2's job — a locale that *drops* an
argument the reference uses is a sentence missing the thing it is about.

Every locale's generated module is `const messages: Catalog = { … }`. Therefore:

- a **missing** key is a missing-property error;
- an **extra** key is an excess-property error;
- a message that uses an argument the reference locale does not have is a property error on
  `d`, because the parameter's type is contextual.

That last one is new and strictly stronger than the old interface: `Strings` could only
check *that* a key existed and its function arity. It could not check that `en`'s
`hoppedTo` interpolates the same two things `ar`'s does.

There is **no runtime lookup and no fallback chain**. `t.hoppedTo` is a direct property of
a compiled object. There is no code path that can miss and substitute another locale.

### Lock 2 — `gate:i18n`: the generated files are in step, and the plurals are complete

`tsc` only sees the generated files. Four ways to defeat it, each closed by the gate
(`scripts/gate-i18n.mjs`, registered in `package.json` `gates`, the `Makefile` `ci` target,
and `.github/workflows/ci.yml` — a gate in one of the three does not run):

1. **Regenerate and diff.** The gate re-runs the generator into memory and fails if any
   committed `*.gen.ts` differs. Editing generated output by hand, or editing a catalog and
   forgetting `pnpm i18n:build`, fails the build. Same discipline as the ETL-output check
   already in `make ci`.
2. **Key sets.** Every locale's key set must equal the reference locale's, reported as
   missing/extra lists rather than a diff. This is the guarantee stated in the locale's own
   terms, so it fails *before* someone regenerates and gets a wall of TypeScript.
3. **Plural categories.** For every `{x, plural, …}` in every locale, the gate asks
   `Intl.PluralRules(locale).resolvedOptions().pluralCategories` and fails if a category is
   unhandled. This is the §② guarantee made mechanical: an Arabic message that handles
   `one/other` and lets `two`, `few` and `many` fall through to `other` does not build.
   (`other` is required by ICU; explicit `=0`-style exact matches are honoured and do not
   satisfy a category. The reverse is checked too: a case for a category the locale never
   selects — `two` in English — is dead code and fails.)
4. **Dropped placeholders and disagreeing branches.** A locale must *use* every argument
   the reference uses, because «انتقلت إلى البقرة · صفحة 7» translated as "Hopped to a
   similar verse" is a valid ICU message and a broken announcement. And a `select` must
   offer the same case set in every locale, because the caller passes one value and every
   language has to accept it.

### Lock 3 — the unit test that walks every locale

`i18n.test.tsx` already walks the bundles calling every formatter with stand-ins, so a new
key is covered the day it exists. It now walks **`LOCALES`** rather than a hard-coded pair,
so a locale added without a translation is a failing test rather than an untested one.

### Proving it bites

Not asserted — induced. Remove one key from `apps/web/src/messages/en.json`, run
`pnpm typecheck` and `pnpm gate:i18n`, watch both fail, put it back. The exact output is
recorded in `docs/decisions/i18n.md`. Do this again if you change any of the three locks;
a guarantee nobody has watched fail is a guarantee nobody has.

## ⑤ The boundary: what is translatable, and what is not

The UI language moves the **chrome** and nothing else (`lang.ts` has the long form). Four
things sit outside the translation layer, for four different reasons.

**Licence attribution — machine-enforced.** `gate:license-copy` binds every `CREDITS` row
in `components/Colophon.tsx` byte-for-byte to a ` ```colophon ` fence in `SOURCES.md`.
Routing an attribution through the translation layer breaks that gate, and it should: an
attribution that reads differently depending on the reader is not an attribution anyone
made. It is a legal string, not copy. These rows are not in the catalog and must not be.
The surrounding chrome (`licenceHead`, `aboutFoot`, the sheet's title) *is* copy and *is*
translated — the boundary is the row, not the sheet.

**Scripture and ayah text.** The mus'haf is an image of a printed page. `DiffView` pins
`lang="ar" dir="rtl"` on verse text in every UI language. There is nothing to translate
because Hifth does not render translations of the Qur'an — it is a navigation instrument,
and a rendering of scripture in the reader's language would be a different product with a
different licensing story.

**Edition proper names.** `hafs-kfqc` is «حفص» / "Hafs · King Fahd Complex" — the *name of a
printed edition*, not a description of one. These live in `apps/web/src/editions.ts` as a
per-locale override table, deliberately partial: Arabic supplies none, because
`@hifth/core`'s own strings are already the Arabic names. A partial table is exactly the
shape the catalog's completeness rule forbids, which is the second reason it is not in the
catalog — an override that is *absent on purpose* and a translation that is *missing by
accident* must not look alike. Each locale still has to declare its table, even as `{}`, so
"no overrides" stays a decision.

**Tajweed rule names.** «إدغام» / "idgham" are the same name written two ways, and both ship
in both languages — only the order changes, because a rule name is what a teacher says out
loud and the Latin spelling is how it is written down. That ordering is a property of the
*locale*, not a string: `LOCALES[lang].rulePrimary` is `"arabic"` or `"latin"`, and a new
locale must choose.

## ⑥ Numerals and direction are properties of a locale

### Numerals

The Arabic UI uses Arabic-Indic digits everywhere **including inside `aria-label`s** — the
half that is easy to forget, and the half a screen reader mispronounces when it is missed.
The hop rail once said «٣» to the eye and "three" to a screen reader, and the only place the
two spellings ever sat side by side was an aria snapshot.

So: **`format.ts`'s `digits(n, lang)` is the single authority on numerals, and the message
layer never formats a number.** Two rules follow, and the emitter enforces both:

- ICU's `#` (octothorpe) and `{n, number}` are **rejected by the generator with an error**.
  Both would route through `Intl.NumberFormat`, which is a second numeral authority with
  different answers — `Intl.NumberFormat("ar").format(1000)` is «١٬٠٠٠» with a U+066C
  separator; `digits(1000, "ar")` is «١٠٠٠». Two authorities is how the aria-label defect
  happened the first time.
- A message that pluralises therefore takes **two** arguments: the number, for CLDR
  selection, and the already-formatted digit string, for printing. The convention is a
  bare name for the number and the same name with a `Text` suffix for the digits —
  `{n}`/`{nText}`, `{count}`/`{countText}`, `{ayahs}`/`{ayahsText}`. It looks redundant and
  is not: `{n}` selects, `{nText}` prints, and `Intl.NumberFormat` never enters the bundle.
  A message that only *prints* a count and never agrees with it — Arabic's
  `legendCountOnPage`, «{nText} آية في صفحة {pageText}» — takes only the `Text` form, and
  English's version of the same key adds `{n}` for its own `{n, plural, …}`. `Catalog`
  types the **union** across locales, so the caller passes what any language might need.

**The deliberate exception: page numbers are Latin digits in both languages.** «صفحة 7», not
«صفحة ٧». A page number is the one figure a reader reads off the corner of the printed
mus'haf and types into the jumper, and the chrome's `.numeric` treatment has always shown
it that way. In the catalog this is simply a plain `{page}` argument passed the raw number
— string-concatenated, never routed through `digits`. `i18n.test.tsx` pins it, and the aria
snapshots record «صفحة 7».

### Direction

`dirOf(lang)` drives the document's direction, and it now reads `LOCALES[lang].dir` rather
than testing for `"en"`. **A locale that does not declare its direction does not compile.**

Direction is per-**chrome**, not global. The stage, hop rail, trail and page bar are pinned
RTL in every UI language — they are mus'haf furniture, and a hafiz whose phone is set to
English must not find the book running backwards (Loop 1's record). `e2e/lang.spec.ts`
asserts the *computed* direction of `main` and `footer` under an English chrome, because the
stylesheet is 100% logical properties and an accidentally inherited flip is a defect no
screenshot would catch.

## ⑦ Adding a locale — the checklist

For someone who has not read this document's history. Say the new locale is `ur` (Urdu).

1. **Copy the catalog.** `cp apps/web/src/messages/ar.json apps/web/src/messages/ur.json`
   and translate the values. Do **not** delete keys you have not got to — an incomplete
   catalog must fail loudly, and it will (§④). The file's presence is what *creates* the
   locale: `Lang` is derived from the catalogs, so there is no union to widen by hand and
   no import to add. `pnpm i18n:build` regenerates `locales.gen.ts` and `catalogs.gen.ts`
   from the directory listing.
2. **Mind the plurals.** Any `{n, plural, …}` block must handle every category
   `Intl.PluralRules("ur").resolvedOptions().pluralCategories` reports — no more and no
   fewer. `gate:i18n` names both the missing and the dead. Urdu is `one, other`; do not
   simply copy Arabic's six.
3. **Regenerate, and let the compiler give you the list.** `pnpm i18n:build && pnpm
   typecheck`. `LOCALES` is `Record<Lang, Locale>`, so it now fails to compile, and the
   error *is* step 4. Commit the generated `*.gen.ts`; they are checked in on purpose, so
   `tsc` and code review both see them.
4. **Declare it.** `apps/web/src/lang.ts` — add a `LOCALES.ur` row: `name` (what the
   language calls itself, *in itself* — never translated), `abbr` (the same, short enough
   for the desktop header's switch — «ع», "EN"; a decision the language makes, not a
   truncation of `name`), `dir` (`"rtl"` for Urdu), `surahNames`, `digits`, and
   `rulePrimary` (§⑤). None of these has a defensible default: a locale silently inheriting
   `ltr` is a mus'haf rendered backwards. `detectLang` then matches `ur` from
   `navigator.languages` with no further change; check the fallback chain still ends at
   Arabic, which is what this app is.

   Both language switches — the colophon's and the desktop header's — are built from
   `LOCALE_IDS` and this row, so they grow a third option with no edit (§⑨ ④). What they
   cannot do for you is the *sentence*: `langSwitchTo` interpolates the new name into the
   offering language's grammar, which is right for `ar` and `en` and may not be for the
   language you are adding (§⑨ ⑤).
5. **Decide the surah-name table.** `format.ts` holds `SURAH_NAMES_AR` and
   `SURAH_NAMES_EN`, and `LOCALES.ur.surahNames` picks one. Urdu reads the Arabic table; a
   Latin-script locale reuses the romanised one or needs its own. A judgement about the
   reader, not a translation task — the names are proper nouns.
6. **Declare the editions table.** `apps/web/src/editions.ts` — add `ur`, even as `{}` (§⑤).
7. **Run the locks.** `pnpm typecheck && pnpm gate:i18n && pnpm test`. Note that
   `i18n.test.tsx` walks `LOCALE_IDS`, so the new locale is under test the moment its
   catalog lands — including "its numerals are the ones it declared".
8. **Check the direction in a browser**, not just in the type. For an RTL locale, confirm
   `main` and `footer` still compute `direction: rtl` (they are pinned; §⑥) and the chrome
   flipped. `e2e/lang.spec.ts` is the pattern; it overrides playwright's `locale: "ar"`
   pin, and a second such file should say why.
9. **Do not regenerate the aria snapshots.** They are recorded in Arabic. A new locale must
   not touch them; if it did, something is reading the wrong catalog.
10. **`docs/map.json`** — the `ui-language` feature's `extend` notes are the thing a future
    reader will actually find. Keep them true.

**Do not add a locale you cannot finish.** A half-empty catalog defeats the guarantee this
whole design exists to preserve, and a demonstration stub is the worst of both: it looks
like proof and it is a hole.

## ⑧ Deliberately out of scope

- **Runtime-loaded catalogs / code-split locales.** All catalogs are statically imported
  and ship in the main bundle. At ~4 KB gz per locale this is right until roughly a dozen
  locales; past that, split by dynamic `import()` keyed on `Lang`. Doing it now would buy
  nothing and cost the app a network round-trip it has spent five loops learning to avoid.
- **Translating scripture, or shipping a Qur'an translation.** Different product,
  different licensing, not this.
- **Dates, times, currencies, relative time.** The app has none. If one arrives, ICU
  `{d, date, …}` is available in the catalog format and the emitter will need a case for it
  — and that case must answer the §⑥ numeral question before it is written.
- **Translation-management tooling** (Crowdin, Weblate, `.po` round-tripping). Flat JSON
  catalogs are the interchange format every such tool reads; adopting one is a later
  decision that this design does not foreclose.
- **A third locale in this change.** The deliverable is the framework and the proof it
  scales. The proof is that nothing hand-written names a locale any more — `Lang`,
  `CATALOGS` and the test suite are all derived from the files in `messages/` — plus
  `gate:i18n` and the induced failures recorded in `docs/decisions/i18n.md`. A stub
  translation would be the worst of both: it looks like proof and it is a hole.

## ⑨ Open questions, and what would answer each

Every design doc in this repo ends under this heading, and every item is an
`### ⓝ … · **status**` row so `pnpm gate:issues` can read it. The vocabulary is defined once
in [`docs/issues.json`](../issues.json).

### ① Arabic number agreement outside `distance` · **open**

§② counts 37 forms Arabic silently substitutes today. The migration preserved every one of
them verbatim, because a migration that also changes wording cannot be reviewed as
behaviour-preserving and would take the aria snapshots with it. They are now one JSON edit
each — but the edit needs a hafiz's eye and its own commit, not this one. **This is a known
defect, deliberately deferred, not an oversight.**

### ② `ar` as the reference locale · **answered**

Correct today: Arabic is the app's native tongue and the richest plural system, so a message
expressible in `ar` is expressible anywhere. It does mean an English-first contributor writes

### ③ `refJoin` («، » / ", ») is punctuation, not copy · **answered**

It is in the catalog anyway because there is nowhere better. If a locale gets this wrong the
symptom is a comma in the wrong script inside a merged row — visible, low-stakes. Left alone.

### ④ `I18n.other` assumes there are exactly two languages · **fixed**

The switch is a toggle, so "the other one" is well defined. The assumption is now named in
one function (`otherLang` in `i18n.tsx`) instead of being spread across the provider, but it
is still an assumption: a third locale turns the toggle into a list and `other` into
`stringsFor(id)` over `LOCALE_IDS`. Cheap to do, deliberately not done blind.

Done, and the "not blind" caveat turned out to be the reason to do it rather than a reason to
wait. Generalising the two radio groups over `LOCALE_IDS` is *behaviour-preserving at two
locales* — the registry's order is `ar` then `en`, which is the order the hand-written buttons
were in, so the rendered markup is unchanged down to the attribute. There was no third locale
to render blind at; there was only an assumption to delete while deleting it cost nothing.

What the assumption would have cost is worth writing down, because it is not the obvious
failure. A third catalog would not have crashed and would not have failed a type-check: the
switch would have rendered two options out of three, and — the quieter half — `otherLang`
returns *one* id, so both non-current buttons would have been labelled «التبديل إلى X» with
the same X. One language missing from the list, and another language's name on a button that
does not select it. Both are wrong output from code that still compiles.

`I18n.other` is gone, not deprecated. A field that is correct only at a particular count is
not a field to leave lying about with a comment on it; the two call sites now ask the registry
directly (`LOCALES[id].name`), and the provider no longer carries a second bundle nobody reads.

Two things came out of the doing. `LOCALES` gained `abbr` — «ع», "EN" — because the desktop
header had been showing hand-typed glyphs that no rule derives from «العربية»; shortening a
language's name is a decision that language makes about itself, exactly like `name`, so it is
declared beside it rather than computed. And the live option keeps its bare text as its
accessible name, deliberately unchanged: the aria snapshots record it, and whether «ع» alone
is enough for a screen reader is a question about that one abbreviation, not about the switch.

*Closed by* `apps/web/src/i18n.test.tsx` — "offers every language there is, not merely the one
this is not" and "names each option after itself, in the language doing the offering", plus
`DesktopChrome.test.tsx`'s registry-driven pair. All four are written over `LOCALE_IDS` rather
than over «العربية» and "English", which is what makes them fail on the day `ur.json` lands
instead of quietly still passing. Verified by inducing each half separately: rendering only
`id !== lang` fails with `expected [ 'ar' ] to deeply equal [ 'ar', 'en' ]`, and labelling with
`LOCALES[lang].name` fails naming the label it could not find.

### ⑤ `langSwitchTo(other)` interpolates a locale's name into another locale's sentence · **answered**

Correct for the two locales present. A language whose grammar inflects the inserted name will
need a different message shape, and ICU cannot fix that — it is a real limit of
interpolation, worth knowing before someone reports it as a bug.

Answered rather than fixed, and the distinction is the point: there is nothing to write. The
message is right for `ar` and `en`, and the repair for a locale that inflects is not a better
interpolation but a different message — one string per offerable language, authored by someone
who speaks the offering language, which is not work that can be done before that locale exists.
Filed here so the day it is reported the answer is "known, and here is what it costs" rather
than a search for a bug in `langSwitchTo`.

Note that ④ made this *narrower*, not wider. The old label came from `other.langName`, so at
three locales the same inflected name would have appeared on two different buttons — one of
them the wrong one. Now each button interpolates its own name, so the only thing still open is
the grammar of the sentence around it. §⑦'s checklist is where a new locale meets it.
