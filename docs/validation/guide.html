On-device pan/zoom + highlight-toggle verdict

perf-verdict-on-device · blocks loop-4b, loop-6b, loop-7

The emulated baseline (~8.3 ms/frame, flat under CPU throttle) structurally cannot see the two real risks: initial raster of a ~170 KB inline SVG on a low-end phone, and re-raster on zoom past the layer's backing store. The rendering-scale decision for 604 pages rests on this and nothing else.

What you need

  • A real phone on the same Wi-Fi as this laptop — a mid/low-tier Android and an older iPhone if you have both; either one alone still answers most of it.
  • No cable, no DevTools, no pairing. The page measures itself.
  • About 3 minutes per device.

Setup — on the laptop

make phone-perf

Builds a throwaway probe bundle, prints On your phone (same Wi-Fi): http://<lan-ip>:4173, then holds the terminal open serving it. Leave it running.

Steps — on the phone

  1. The mushaf page as normal, plus a dark slab pinned across the top reading «قياس الأداء على هذا الجهاز — ١٥ ثانية» with an ابدأ button. No slab means you are on an ordinary build — something else is already serving port 4173; stop it and re-run make phone-perf.

    Confirms you are measuring the build that has the probe in it. An ordinary build looks completely normal, which is exactly how you would not notice — and every number below would then be a measurement of the wrong thing.

  2. «استعد / get ready» for one second before each segment, then the segment's instruction and a countdown. The slab ignores taps while recording, so you cannot accidentally drive it instead of the page.

    The one-second «استعد» beat is there so the tail of one gesture does not land in the head of the next segment. Rush it and the three numbers blur into each other, which is the one way this check can fail without looking like it failed.

  3. The page moves under your finger and the counter runs 5→1. Keep moving: a still finger produces no frames and the segment will report «too few frames — not driven».

    Pan is the cheap case: no re-raster, just compositing a layer that already exists. If pan is over budget then nothing further matters — the page is too heavy as DOM and the verdict is raster-fallback.

  4. Zoom follows the pinch. The re-sharpen moment is the one being measured — it is the layer being re-rastered.

    This is the whole check. Zooming past the layer's backing store makes the browser re-rasterize ~170 KB of glyph paths, and that cost is structurally invisible to the emulated desktop baseline. The rendering decision for all 604 pages turns on this one number.

  5. Amber marker swipes land on each ayah you tap — one along the middle of every line it occupies, with the scripture still readable through them. Different ayahs, not the same one twice — you are measuring overlay churn.

    Separates rendering cost from interaction cost. If only this segment is bad the problem is overlay churn in the highlighter — a real bug, but not one that changes which rendering strategy Loop 4b builds.

  6. «النتيجة — الصقها في ledger.json», a row per segment with mean / fps / p95 / worst / jank (over-budget cells in salmon), and a read-only JSON blob stamped with the device, dpr, cores, standalone flag, build commit, and FCP/LCP. There is no copy button on purpose: a LAN preview is plain http, so the Clipboard API does not exist here.

    The table gives you the verdict; the JSON is what makes it re-checkable a year from now. It stamps device, dpr, cores, standalone flag and build commit, so a later reader can tell whether the number still describes the phone in their hand.

  7. "standalone": true in the second JSON. Standalone gets its own compositor path on iOS, so the two runs can legitimately disagree — that difference is a result, not noise.

    iOS gives standalone its own compositor path. If the two runs disagree, the install prompt is doing load-bearing work rather than convenience work — and that changes what Loop 6b has to guarantee.

Reading the result

  • p95 ≤ 16.7 ms and jank < 10% on all three segments → verdict inline-svg: inline SVG everywhere holds, and Loop 4b is plain vendoring + streaming.
  • Pan fine but pinch p95 much worse → re-raster past the layer's backing store → verdict content-visibility: virtualize off-screen pages; do not rasterize glyphs.
  • Pan itself over budget, or worst > 100 ms on the first pinch → the page is too heavy as DOM → verdict raster-fallback: rasterize the glyph layer, keep the polygon hit layer as DOM (the highlighter API does not change).
  • Only the tap segment is bad → that is INP, not rendering: overlay churn in packages/core/src/highlighter.ts. It does not change the rendering verdict; file it separately.
  • «too few frames — not driven» on any segment → that segment never got a real gesture. Re-run it; a number from an undriven segment is not a result.
  • The two devices disagree → the low-end one decides. The budget exists for the phone that struggles.

Record it

Then do what it tunes:

  • apps/web/perf/pan-zoom-trace.mjs — the frame budget asserted in CI becomes the measured number, not the emulated one
  • docs/PLAN.md §Loop 4b — which of the three rendering strategies gets built

VoiceOver / TalkBack gesture walkthrough

screen-reader-walkthrough · blocks loop-7

axe and the keyboard hop tour cover the machine-checkable floor and are green, but neither can tell you whether a screen-reader user can actually select an ayah and hop. Per-polygon labels are a design bet that has never been heard out loud.

What you need

  • The same phone, with VoiceOver (iOS: Settings → Accessibility → VoiceOver, or triple-click the side button) or TalkBack (Android: Settings → Accessibility).
  • About 8 quiet minutes. You are listening, not looking — the last step asks you to stop looking entirely.
  • The ordinary build, not the probe build.
  • Nothing to memorise. This used to be eight steps; five of them were checking that a control existed under a given name, and those are now aria snapshots in apps/web/e2e/__aria__/{iphone,android}/ that fail the build when a label changes. Reading those five files first is optional and takes a minute — they are exactly what the app should announce.

Setup — on the laptop

make phone

Prints Open on your phone (same Wi-Fi): http://<lan-ip>:4173 and serves the normal app — no perf slab at the top.

Steps — on the phone

  1. «الآية البقرة · ٢:٤٨» — that the label exists and reads exactly this is already asserted by e2e/__aria__/*/page-group.aria.yml. What you are judging is whether it sounds like something you would say, and whether your voice speaks ٢:٤٨ correctly rather than as "two colon four eight" or as a year.

    The one thing no linter can check. axe proves a label exists and the snapshot proves it has not changed; only an ear can tell you the phrase is one a person would use, and only a real voice engine tells you how Arabic-Indic digits actually come out.

  2. Both swipes stay inside the sheet — neither walks you into the page behind it. After the hop, the next swipe lands on something real on the new page, not on a node from the sheet that no longer exists.

    Focus containment and focus survival across a page change are the two failures that make hopping unusable without sight, and neither is visible to a runner: the tree is correct in both the working and the broken case. The sheet's own contents — «إغلاق», «انتقل إلى …» — are pinned in e2e/__aria__/*/hop-popover.aria.yml and are not what you are checking here.

  3. You can do it. Whatever you could not do — or could only do because you already knew where things were — is the result of this check.

    Every label can be correct and the app still unusable, because you knew where to swipe. This is the actual verdict; the two steps before it are how you find out why it failed.

Reading the result

  • A label that reads awkwardly, or digits your voice speaks wrongly → change the label in packages/core/src/highlighter.ts (enhancePolygons) or the component that owns it, then regenerate the aria snapshots (pnpm -C apps/web exec playwright test share-a11y --update-snapshots) and read the diff — it is the new announcement, written down.
  • Focus escaping a sheet, or stranded after a hop → an e2e assertion, not a label change. The tree is already correct in both cases, which is exactly why this half stayed human.
  • A control announced in the wrong order or not at all → that is a snapshot failure and should have failed CI before you picked up the phone. If it did not, the surface is missing from the aria-snapshot set — add it to apps/web/e2e/share-a11y.spec.ts.
  • A tour you could complete but found exhausting → write that in result anyway. Feel is not a bug report, but it is exactly what this check can see and axe cannot.
  • Nothing wrong at all → say which reader, which OS version, and which phone. A pass on VoiceOver 17 is not a pass on TalkBack.

Record it

make record CHECK=screen-reader-walkthrough RESULT='VoiceOver iOS 17 on iPhone SE — full tour by gesture; ayah labels read «الآية البقرة · ٢:٤٨» (fine); rail chips read as words; one finding: <…>'

Then do what it tunes:

  • apps/web/e2e/__aria__/ — the pinned trees. Delivered ahead of this check (2026-07-27); a phrasing verdict lands here as a regenerated snapshot, which is the announcement written down
  • apps/web/e2e/share-a11y.spec.ts — a surface with no snapshot yet, or a focus behaviour you could break, becomes a test there
  • packages/core/src/highlighter.ts — the aria-label shape, if the labels read badly

Edge spot-audit — 20 sampled pairs against a printed mushaf

edge-spot-audit · blocks web-v1.0 · repeats every 14 days

The data is scripture. Every automated gate here proves the shards are well-formed; none can prove an edge is true. This is the only check that can, and it is the one whose results are worth the most per minute spent.

Already done for you

pnpm gate:verified-edges

pass · 2026-07-29 · bc365d3 · darwin · node v20.19.4 — 1 step(s) below are struck through

What it cannot do — still yours:

  • Every pair. The gate re-checks verdicts that are already banked against the shipped corpus; it cannot look at a mushaf, and no verdict exists until someone has. This is the one check in the register that can establish the data is true, and it is human by construction.
  • Choosing what to look at. make validate prints which strata have never been audited — a class with no verdict in it is a class where a wrong pair survives every check this repo has — but pointing at the gap is not closing it.

What you need

  • A printed mushaf — the KFGQPC Hafs print the pages are photographed from, so page numbers line up. No paper? .claude/skills/mushaf-reference/SKILL.md names the published scans and page tables that stand in, and — more importantly — which ones are a different qira'a or a different print revision and will make a correct pair look wrong.
  • 30–45 minutes for twenty edges. A hafiz if you can get one; this is the check where a second reader is worth the most.
  • Nothing else — the draw runs here.

Setup — on the laptop

make validate

Ends with an edge-audit coverage table: one row per class of edge (type × curated-or-dataset × page distance), each marked ✓ or ·. The · rows are the classes nobody has ever looked at — those are what this round is for.

make audit-edges N=20 SEED=1

A header naming the edition, the seed, and the rerun command, then twenty numbered pairs — from → to type p.<page> / p.<page> curated|dataset words <n> roots <n>/<n> — then a JSON block ready to paste. Use a fresh SEED per round; add NEW=1 to draw only from pairs no verdict has settled.

Steps — on the phone

  1. Each from and to is findable at the page printed beside it. A pair you cannot locate is itself a finding — record it as wrong with a note.

    This is the only check in the project that can say the data is true. Every other tier verifies that the app faithfully renders whatever the ETL produced — including when what it produced is wrong.

  2. words is the longest run of words the two ayahs share — the same score gate:edges enforces a floor on, computed by the same reader (packages/etl/scripts/morphology.mjs), so a number here can never disagree with CI. roots is how many of the shorter ayah's roots appear in both, in order.

    They point at the pairs worth slowing down on from both ends: a high words with a wrong verdict is a plausible-looking false edge, and a low one that is nonetheless right is the case the product exists for — 2:48 → 2:123 swaps شفاعة and عدل, scores 1, and is genuinely confused by huffaz every day.

  3. Most edges are obvious either way in a few seconds. The slow ones are the informative ones; note why.

    "Similar" is not the standard; a hafiz's confusion is. An edge that is textually close but never actually confused is noise in the rail, and noise is what makes a reader stop trusting the hop.

  4. The edge appears as a hop under the direction chip its type implies.

    Catches a correct edge with a wrong presentation. A real mutashabih filed under the wrong direction chip sends the reader looking in the wrong surah, which reads as bad data even though the data is fine.

  5. Forty entries for twenty pairs — the block writes out both directions of each pair, because every edge in the corpus is generated in both and one reading settles both.

    Recording the correct verdicts matters as much as the failures: they are what turns half an hour of reading into a permanent regression fixture instead of an anecdote.

  6. Run pnpm gate:verified-edges.

    Done by pnpm gate:verified-edges on 2026-07-29. Skip it.

Reading the result

  • Record BOTH verdicts. A rejected edge that is not written down comes back on the next data refresh and costs the reader's time all over again — and no automated check can tell a wrong edge from a right one.
  • If several wrong edges share a shape — same type, same phrase length, same surah pair — that is a filter in packages/etl/scripts/build-adjacency.mjs, not twenty more rejections. A class of error is worth more than the twenty.
  • If gate:verified-edges fails later, do not edit the fixture to go green: the data moved under a human verdict. Find out what moved it, and re-verify with a reader before changing a verdict.
  • This check goes stale after 14 days because the data keeps moving. A fresh seed each round means the coverage accumulates instead of re-checking the same twenty.
  • Look a pair up by KEY, not by page, in whatever reference you use. Our print is QCF V2/1421H and most published tables are V1/1405H; they place different ayahs on 36 pages, so a page-based lookup in the 583–600 band finds the wrong ayah and the pair reads as wrong data. make probe-reference ALL=1 asserts that divergence is still exactly the expected 36 and nothing else moved — it settles the arithmetic under this check, and none of the judgement.
  • Aim at the · rows. The draw is stratified for a reason: 97% of the corpus is one class (dataset mutashabih, far apart), so a flat draw of twenty essentially never shows a shared-root edge, a related-meaning edge, or a pair we curated ourselves — and those are exactly the classes no automated check covers, since gate:edges deliberately does not score shared-root at all. Pass UNIFORM=1 only when the overall *rate* of bad edges is the question, and note that gate:edges already carries the rate on every commit.

8+ day offline survival, installed vs browser tab

offline-survival-8-day · blocks loop-6b

Safari's ITP deletes all script storage for origins untouched for 7 days of browser use, and Home-Screen-installed apps are exempt. That single asymmetry is why the install prompt is a feature and not a nicety — and it has never been observed, only read about.

What you need

  • Runnable as of Loop 6b. The button exists: open the page chip in the header, the sheet «ما فتحتَه من المصحف», the «جزء» scope, then «احفظ الجزء ١ هنا» at the top. Pin juz 1 in both buckets — it is what the e2e pins, so a discrepancy is comparable against something, and it is ~2.9 MB, which is small enough to re-pin over a masjid connection if the day-8 answer is bad. What is already asserted without a phone — visited pages surviving a reload offline, the app recovering from an eviction, and a pinned juz opening a never-visited page with the radio off — is in apps/web/e2e/offline.spec.ts. All that is left here is the waiting.
  • What the eight days no longer have to find. Research ④ replaced the *eviction* half of this check with Storage.clearDataForOrigin over CDP, which takes the origin's caches out from under a live page exactly as a sweep does. That found two real defects (the precache never rebuilt after eviction, so one sweep ended offline support permanently; and a page that failed to fetch left the chrome claiming a page the stage was not showing). Both are fixed and asserted in the Hifth · eviction describe. So this check is now only about the thing no harness can supply: whether iOS actually sweeps an uninstalled origin at ~7 days and spares an installed one.
  • An iPhone (the ITP asymmetry is Safari's), and a deployed build.
  • Eight days of ordinary phone use. The clock counts days of *browser use*, not calendar days — a phone left in a drawer does not run this experiment.

Steps — on the phone

  1. The button becomes a count («جارٍ حفظ الجزء ١ — ن من ٢٤») with «إيقاف» beside it, and settles into a row reading «الجزء ١ · ٣٫١ م.ب» or thereabouts — the offer disappears, because the juz is now kept. If the row instead says «ناقص» the pin did not finish; press «احفظه من جديد» before starting the clock.

    The tab is the case we expect to lose. Proving it worked on day 0 is what makes a day-8 failure evidence rather than a guess.

  2. Two independent storage buckets now hold the same pack. That is the experiment.

    Two buckets, same pack, same phone, same eight days. It is the only arrangement that lets you attribute a loss to the storage sweep rather than to the network, the build, or the device.

  3. Nothing. This step is the check.

    ITP counts seven days of browser use, not seven days of wall clock, and it cannot be fast-forwarded. The waiting is the instrument.

  4. The tab may have lost everything (ITP clears script storage for origins untouched for 7 days of browser use). If it has, the notice «الصفحات التي حفظتها لم تعد في هذا الجهاز» should be on screen with «اعرض المحفوظ» beside it, and under «المحفوظ في هذا الجهاز» the row for juz 1 should read «لم يعد في هذا الجهاز» or «ناقص» — not a broken page, and not a row still claiming megabytes it no longer has.

    Airplane mode is what makes this a storage test rather than a cache test: whatever still works is genuinely resident on the device.

  5. The juz is still there. Installed apps are exempt from that sweep — this asymmetry is the whole reason the install prompt is first-class.

    If the installed app survives and the tab does not, the install prompt stops being a nicety and becomes the feature that makes offline revision real — which is what Loop 6b has to be designed around.

Reading the result

  • Tab evicted, install survived → the assumption holds. Assert the eviction-detection path in apps/web/e2e/offline.spec.ts and keep the install prompt prominent.
  • Both survived → note the exact iOS version; the rule may have relaxed. The install prompt's copy then becomes a nudge rather than a warning, which is a copy change, not an architecture one.
  • The installed app was evicted too → the re-pin offer's trigger in apps/web/src/storage.ts is now urgent rather than theoretical, and the offline story needs rethinking before any 'works offline' claim ships.
  • Anything showed a broken page instead of an offer to re-pin → that is the bug, whichever bucket it happened in.

  • apps/web/src/pwa.ts — repairShellCache() re-registers sw.js under a query-suffixed URL, because a script URL the registration has never seen is the only thing observed to force the install that refills an evicted precache. Two days of real revision produce two days in the record

revision-record-lands-on-a-phone · blocks loop-7

The revision record is tested against fake-indexeddb in Node, where the clock is a parameter, nothing evicts, and every write lands. All three are false on a phone. Three specific things can only be seen there: whether a write inside a tap gesture survives the app being swiped away seconds later (iOS kills backgrounded tabs aggressively, and the store deliberately writes per tap rather than batching precisely because of that); whether a day boundary in the record matches the day boundary the reader lived through, since dayOf files by the offset captured at record time and nothing in CI has ever run under a non-UTC clock; and whether the whole log is still there a week later, given that iOS deletes script-writable storage after 7 days of no interaction — the exact condition a 'what have I not touched in weeks' view exists to report on. A record that quietly resets and says nothing is worse than no record: it tells a hafiz they have revised nothing.

What you need

  • A phone — an iPhone if you have one, since the seven-day sweep is Safari's and it is the failure this check is mostly about.
  • A deployed build, and two calendar days. The second session must be on a different local day from the first; that is the whole point of the first three steps.
  • There is no picture yet. Task #91 is gated on Loop 4b, so the record is read back through the browser's own IndexedDB inspector rather than through a view in the app. Safari: connect the phone to a Mac and use Web Inspector › Storage › Indexed Databases › hifth.revision.v1. Chrome on Android: chrome://inspect from a desktop, then Application › IndexedDB. The days store is keyed by YYYY-MM-DD; the meta store holds one row, since.
  • What no harness can supply. revision-store.test.ts proves the retention window, the since stamp and per-tap durability against a real IndexedDB implementation, and App.test.tsx proves the three exclusions through the real UI. None of that runs under a phone's clock, a phone's storage pressure, or a phone's process killer.

Steps — on the phone

  1. A row already exists, stamped with today's local date — written by opening the store, not by any tap.

    This is the entire defence against the seven-day sweep. A record that has existed for a month and holds nothing means the reader did not tap; one that has existed since this morning and holds nothing means we lost it. If since only appeared after the first tap, those two are indistinguishable forever after.

  2. Under days → today's date: one entry per ayah you selected, exactly one entry for the whole marquee (carrying both a key and an endKey), and nothing at all for the tap that dismissed.

    The three exclusions are asserted in App.test.tsx, but against a synthetic pointerup on a fixture page. This is the same claim against a finger on the real gesture stack — where a marquee release and a tap are told apart by @use-gesture, not by the test calling one or the other.

  3. Reopen and inspect: those last taps are all present.

    The store writes on every tap instead of batching, which costs a rewrite of the day's array per tap. This step is what that cost is buying. A batched writer loses exactly the taps made just before the app is killed, which on a phone is most of them — and it would have looked perfect in every test in this repo.

  4. Looks before midnight file under the earlier date and looks after it under the later one — by the phone's own clock, not UTC.

    Every clock in CI is UTC, so dayOf reading the offset from the event has never once been exercised against a real one. Someone revising at 23:40 in a UTC+3 city and again at 00:20 has revised on two days; if the record shows one, the offset is not riding on the event and every evening session east or west of Greenwich is mis-filed.

  5. days now holds two keys, the earlier one unchanged, and meta → since still shows the first day — it must not have moved forward.

    since moving with the record would make the log look freshly created every time it was read, which is precisely the wipe's signature. This is the cheapest way to catch that, and it cannot be caught at all in a suite that creates a new database per test.

  6. Either the record is intact, or it is empty and since reads as today — never empty with an old since.

    This is the failure the feature is designed around and the one no harness can produce: iOS sweeping an origin nobody has touched. The two acceptable outcomes are 'the history is there' and 'the history is gone and the record admits it is one day old'. The third — empty, with a since from weeks ago — is the app telling someone they have not revised in a month. Note whether the phone had the site installed to the Home Screen or open as a tab; that is the same asymmetry offline-survival-8-day measures for the page cache, and this is the IndexedDB half of it.

Reading the result

  • Everything as expected → the record is real on a device. Loop 4b can proceed to task #91 (RevisionMap) on the understanding that the numbers behind the picture are true.
  • Taps lost after a swipe-away → per-tap durability is not enough on this OS. That is a recordLook problem, not a UI one, and it must be fixed before any picture is drawn from the data.
  • The near-midnight session filed under the wrong day → tz is not reaching the event. Everything else in the record is then wrong by up to a day for every reader not on UTC, which is almost all of them.
  • Record empty with a stale since → the store's own defence failed, and no view may render the record until it is fixed. Say what the storage inspector showed; the shape of what survived is the diagnosis.
  • Record empty with today's since → the sweep happened and the record told the truth about it. That is a pass for this check and a hard requirement on #91: the picture must render 'we cannot know' differently from 'you did not revise'.

Record it

make record CHECK=revision-record-lands-on-a-phone RESULT='<iOS|Android> <ver>, <installed|tab>, sessions <date> + <date> — per-tap after swipe-away: <kept|lost>; midnight filing: <correct|wrong|not tested>; after 8 days: <intact|empty+fresh since|empty+stale since>'

Then do what it tunes:

  • apps/web/src/revision-store.test.ts — the retention and since tests are written against a clock passed in as a parameter. Whatever the phone actually did to the log gets a case here, in the units the phone reported it in.
  • packages/core/src/revision.test.ts — the DST/offset cases were reasoned about, not observed. Replace the invented offsets with the real one from the near-midnight session.
  • packages/core/src/revision.ts — RevisionEvent's doc comment lists what must not become an event. If the phone shows a gesture this repo did not anticipate producing a look, that list is what changes.
  • apps/web/src/revision-store.ts — if a swipe-away loses taps, the per-tap write is not sufficient and the durability comment at the top of the file is currently a claim rather than a fact.
  • docs/map.json → revision-record — the extend steps for task #91 depend on which of the two acceptable outcomes actually happens at day eight.

Placement correction by eye — a hundred forced choices between the corrected box and the one we ship

placement-correction-by-eye · blocks mark-C

The measurement says nearly every mark rectangle sits about a letter away from its own ink, and that one number per page fixes it. Only arithmetic has ever said so, and it marked its own homework: the rasteriser that found the displacement is the rasteriser that scores the correction. Nobody has looked at a single verdict. Until somebody does, the thresholds in the placement record stay unenforced, and nothing that points at a mark can ship — which is the whole reason to hold three hundred thousand rectangles.

What you need

  • Both printings on this machine: the pages the app ships, and the gitignored ligature cache the mark boxes are read from. If the placement measurement has ever run here, they are already present; if not, the first setup command says so and stops.
  • About twenty minutes, in as few sittings as you can manage. A hundred trials is roughly thirteen minutes of looking; the rest is settling in.
  • A screen you are not squinting at, and no opinion about what the answer ought to be. Nothing else — no mushaf, no phone, no network.
  • Nobody has to be a hafiz for this one. It is a question about where a rectangle sits, not about what the mark says.

Setup — on the laptop

node packages/etl/scripts/probe-mark-ink.mjs --sample 4000 --seed 7 --pages-n 40

About fifty seconds, ending in a failure code — that is expected, and it is the reason this check exists. It writes packages/etl/out/mark-shift.json: one measured displacement for each of forty pages. That file is the thing on trial.

pnpm adjudicate:marks --seed 11 --count 100

packages/etl/out/mark-adjudication.html in about a second, and a line naming the seed, how many pages the trials spread over, and a short fingerprint of the displacements. Note the fingerprint. Open the file in any browser — it needs nothing running, and it reaches no network.

Steps — on the phone

  1. A first trial: one mark, drawn twice side by side, a rectangle on each, and two keys.

    The trials are built so that nothing on the screen says which rectangle is ours, and the answers exist nowhere until the scorer runs. Reading the builder first is the one way to spoil that, and there is no way to unspoil it — the session would have to be thrown away and rebuilt under a seed you had not seen.

  2. No feedback, ever: the next trial, and a bar creeping along. Some pairs are obvious. Most are not, and a few are the same rectangle twice, where space is the only honest answer.

    Feedback would turn this into training. Within twenty trials a person who is told they were right learns which way the corrected box tends to sit and answers from that rule rather than from the ink, and the count that comes out measures how well they learned it. Space is not a wasted trial: it is left out of the arithmetic rather than counted as a miss, so guessing to keep the tally up is the one thing that would cost you.

  3. The tick lights up and clears itself on the next trial. It changes nothing else on the screen, and it never skips the trial.

    A rectangle can be in the right place and still be the wrong size, and this whole session is about where they sit. Those are two faults with two different repairs, so a fourth button meaning 'wrong somehow' would blend them into one count nobody could act on — and it would eat the trials that still carry a usable answer, because which of two wrong rectangles is closer is a question you can answer. The tick is counted on its own line and the marks you tick are named, so somebody can go and look at those boxes rather than argue about whether they exist.

  4. It resumes on the trial you left, with the answers you already gave. Nothing reshuffles.

    Pushing through a hundred trials tired means the last thirty are answered from fatigue, and in the numbers fatigue is indistinguishable from 'the correction does not help' — it would read as a finding about our data rather than about the hour.

  5. mark-ruling-11.json in your downloads. It holds your answers, the seed, and the fingerprint — and no key, because there still isn't one.

    The ruling is deliberately worthless on its own. That is what makes it evidence: it could not have been edited towards an answer, because at the moment it was written nothing on the machine knew what the answers were.

  6. Four lines with intervals — as shipped, the decoy, the catches, twins — then, if you ticked any, how many marks poked out of both rectangles and the headline again without them. One sentence of verdict at the end. It exits 0 only when the session was valid and the corrected rectangle actually won.

    This is the first moment anyone knows what the right answers were, you included. If it refuses outright, the displacements were re-measured between building the page and scoring it: score against the file it was built from, or build a fresh session and work it again. A ruling scored against displacements it was not worked against comes out looking clean and means nothing.

  7. The ledger gains the four numbers and the date, and this check stops being pending.

    A refusal is worth as much here as a confirmation and is far more likely to be dropped on the floor. 'A person looked and did not prefer our correction' is the single most valuable sentence this project could learn about the mark layer, and it is unrecoverable a week later if nobody wrote the numbers down.

Reading the result

  • 'The correction is supported' → adopt the per-page displacement. The two numbers per page get recorded beside the fit, and the measurement's thresholds become something a gate is allowed to enforce, which is the change this check unlocks.
  • 'NOT supported, and the decoys say why' → the strongest result this can produce, and the reason it is worth twenty minutes. It means you could see a shift of that size perfectly well and still did not prefer ours: our correction is wrong, not the test blunt. Do not adopt it, and say so in the placement record — a rejected option with a measured reason is a settled question.
  • 'cannot see a shift this small' → the session says nothing about the correction either way. Try once more with bigger panels (--panel 640). If the decoys still do not clear half, the difference is below what an eye resolves at this size and no number of trials will change that; the case for the correction then rests entirely on the ink arithmetic and its control, and that is what the record should say rather than pretending this was run.
  • 'SESSION INVALID' or 'SUSPECT' → discard it and do not argue with it. The catches are rectangles a whole letter off their mark and everyone gets those right while looking; missing them means the session was worked while distracted. Rerun under a different seed, which draws different marks in a different order.
  • A run of 'neither box closed on it' is a second finding, and it does not change the verdict above — it starts a different question. The rectangles come from one printing and the ink from another, so a box can arrive in the right place and the wrong size, and no amount of moving it will help. If the count is more than a handful, open the named marks in the encoding inspector and compare the box against the ink before adopting anything; the repair is a re-measurement, not a displacement.
  • One session is one person. If the verdict is going to decide whether marks ship, a second reader under a different seed costs another twenty minutes and turns one person's eyes into a result — and two people disagreeing is itself the finding.

Record it

make record CHECK=placement-correction-by-eye RESULT='seed 11 · 100 trials · as shipped <pct> [<lo>–<hi>], decoy <pct>, catches <pct>, twins <pct> → <supported|not supported|says nothing>'

Then do what it tunes:

  • packages/etl/data/pages/word-boxes.pin.json — a supported correction is two more numbers per page recorded there. This is the artifact the check exists to release.
  • packages/etl/scripts/probe-mark-ink.mjs — its thresholds exit non-zero today and are wired into nothing. A verdict here is the named prerequisite for turning them into a gate.
  • docs/design/mark-registration.md §⑦ — the recommendation is provisional pending exactly this, and §⑩ ① is this question.
  • packages/etl/scripts/lib/adjudication.mjs — an invalid session tunes the mix of trials, not the conclusion about the marks.

Placement by hand — put each rectangle where it belongs, and measure how far our correction still misses

placement-residual-by-hand · blocks mark-C

The forced-choice session can settle whether our proposed move is preferred to what ships. It cannot settle whether it is far enough, because the only two answers on offer are the two we thought of: a correction that points the right way and falls a third short wins every trial and is still wrong, and nothing in that session can say so. This asks for a placement instead of a preference, and the gap between where a reader puts a rectangle and where we wanted it is a distance in page units — a number that can be applied to the boxes rather than voted on.

Verdict 2026-08-12: seed 23 · 60 placements over 40 pages · nearer ours 98.3% [91.1–99.7] · residual (-0.073, -0.110) units against a precision of 0.03, but clustered by the pages they came from neither component clears nought (down [-0.230, +0.009], across [-0.223, +0.077]) → adopt the correction as measured, do not apply the residual. Two further limits the sitting could not see past: the 40 pages placed on are the same 40 the correction was fitted to, so nothing here speaks for the other 564; and those pages all propose nearly the same move, so whether the correction is the right size was not measured at all. Ruled out along the way, and worth not re-buying: it is not the mark's name, not a scale error across the page, not the starting point, and not fatigue.

What you need

  • The same two printings the forced-choice check wants: the pages the app ships, and the gitignored ligature cache the mark boxes are read from. If that check has been run here, nothing more is needed.
  • About twenty-five minutes. Placing is slower than choosing — around fifteen seconds a mark once you have the feel of it — and rushing shows up in the numbers as a wandering hand rather than as an answer.
  • A mouse or a trackpad you are comfortable with, or a touchscreen. Not a phone: the panel wants to be large, and the whole measurement is in fractions of a letter.
  • Nobody has to be a hafiz for this one either. It is a question about where a rectangle sits.

Setup — on the laptop

node packages/etl/scripts/probe-mark-ink.mjs --sample 4000 --seed 7 --pages-n 40

About fifty seconds, ending in a failure code — expected, and the reason this check exists. It writes packages/etl/out/mark-shift.json. Skip this if you have already run it for the forced-choice check and have not touched it since; re-measuring between building a session and reading it makes both of them meaningless.

pnpm nudge:marks --seed 23 --count 60

packages/etl/out/mark-nudge.html in about a second, and a line naming the seed, how many marks come round twice, and a short fingerprint of the displacements. Note the fingerprint. Open the file in any browser — it needs nothing running and reaches no network.

Steps — on the phone

  1. Nothing on the screen tells you either way. This one is on you.

    The two sessions ask about the same rectangles from opposite directions, and each is fair on its own, but placing sixty of them by hand teaches you which way the correction tends to go. Carrying that into a forced choice means answering from the rule rather than from the ink — which is the one failure neither session can detect afterwards, because a person answering from a learned rule looks exactly like a person who can see very well.

  2. A first trial: a line naming one mark, a small piece of print with that mark's letters under a soft blue wash, one red rectangle sitting obviously off it, and a button that will not do anything yet.

    The builder knows where we think each rectangle goes, and this page deliberately does not. Reading it first is the one way to spoil that, and the session would have to be thrown away and rebuilt under a seed you had not seen.

  3. The button wakes up as soon as you move it, and nothing at all happens when you place it except the next trial. No target, no snapping, no 'close'.

    The rectangle always starts in the wrong place, so leaving it alone is never an answer — that is why the button stays dead until you move. And a crop this size holds several marks, often two of the same name, so the line names one and the blue wash points at the letters it belongs to: a placement on the neighbouring mark is a whole letter out and would be recorded as though the boxes were a whole letter out. The wash is deliberately too soft to line the rectangle up against, because anything crisp enough to line up against would be showing you where we think the box goes.

  4. Some marks come round a second time, starting somewhere else. You may or may not notice.

    The pair is the scale for everything else. Two independent goes at the same mark differ by however much your hand wanders, and that spread is what tells a real offset from noise — a residual of a fifth of a unit is a finding if you are repeatable to a fiftieth and nothing at all if you wander by half. Trying to reproduce your earlier answer replaces a measurement of your hand with a measurement of your memory, and then nothing below has a scale.

  5. The tick lights up and clears itself on the next trial. It never costs the placement.

    The same separation the forced-choice session keeps: where a box sits and how big it is are two faults with two repairs, and this whole session measures the first. The tick is counted on its own line and the marks are named, so somebody can go and look at those boxes instead of arguing about whether they exist.

  6. It resumes on the placement you left, with the ones you already made. Nothing reshuffles.

    A tired hand wanders, and a wandering hand does not read as fatigue in the output — it reads as a wide precision estimate, which quietly makes every real finding un-detectable. Better to lose the evening than to spend it widening your own error bars.

  7. mark-placements-23.json arrives in your downloads. It holds where you put each rectangle and where each one started, plus the seed and the fingerprint — and nothing about where we thought they went. In the repo it becomes docs/validation/rulings/<when>-placement-residual-by-hand.seed23.json.

    Same property as the forced-choice ruling, for the same reason: at the moment it was written, nothing on the machine that wrote it knew the answer, so it could not have been edited toward one. And it does not stay in a downloads folder, because every number banked below is derived from it — a verdict whose working lives on one laptop until the browser clears it is a verdict nobody else can argue with. docs/validation/rulings/README.md says what else belongs there.

  8. It opens with which pages the session can speak for, then a headline in the same currency the forced choice uses — how often you landed nearer our correction than the shipped box — then the residual on each axis with two intervals, one treating every placement as its own fact and one clustered by the page it came from. Read the clustered one. Then your own precision from the repeated marks, whether the proposed move is the right size, and a list of the things that turn out not to explain what is left over. It exits 0 only when the placements went the right way.

    This is the first moment anyone knows what the correction was, you included. If it refuses outright, the displacements were re-measured between building the session and reading it: read it against the file it was built from, or build a fresh session and place them again.

  9. The ledger gains the residual, the precision it was read against, and the date, and this check stops being pending.

    The residual is the only number in this project that says how far the mark boxes should move, as opposed to whether they should. Unbanked it has to be bought again at twenty-five minutes of somebody's attention, and a number nobody wrote down is a number nobody will trust the second time either.

Reading the result

  • 'the residual is inside this hand's own precision' → our correction is as close as this session can resolve. Adopt it as proposed and say in the placement record that a reader placing by hand could not distinguish it from their own wobble — which is a result, and is not the same as the correction being exactly right.
  • 'the residual is larger than this hand's precision' → a further move on top of what the measurement proposes, but only if the clustered interval says so. Beating the precision floor says the number is bigger than one hand's wobble; it does not say the number is bigger than nought, and those are different claims. Read the line under the residual: it names which components clear nought once the placements are clustered by the pages they came from, and nothing not named there may be applied. When it does say apply, apply it to the recorded displacements and not to the code that computes them — the arithmetic is not what is wrong, the frame it is measured against is, and burying a hand-measured constant inside a rasteriser hides that distinction from whoever reads it next.
  • 'clustered by page, neither component is distinguishable from nought' → adopt the correction and leave the residual alone. Two marks on one page share that page's frame error, so a session of sixty placements over forty pages carries forty pages' worth of information; the interval that counts them as sixty is narrower than the truth. This is not a refutation — most of the interval usually still sits on one side of nought — it is the session declining to settle a distance it never had the sample for. The way to settle it is more pages, not more placements on these ones.
  • 'undecidable from this sample' under the gain → the pages in this session all propose nearly the same correction, so nothing here separates a correction that is exactly right from one that is a fifth short. On pages like these a wrong gain and a constant residual are literally the same number. Do not read the gain, and do not buy more placements on the same pages hoping to sharpen it.
  • The coverage line at the top bounds everything under it. A trial cannot exist without a proposed move and a proposed move only exists for a measured page, so a placing session is always an in-sample check: it says the correction holds where it was fitted, and is structurally incapable of saying it holds anywhere else. If that line reads well short of 604, the next thing this project needs is a wider measurement, not a wider session.
  • 'the correction goes the WRONG way' → stop. Do not adopt anything, and do not reach for a sign flip, which would be fitting the correction to sixty placements by one person. This contradicts the forced-choice session if that one passed, and two instruments disagreeing about the same rectangles is a finding worth more than either of them — write it in the placement record and re-measure before shipping any of it.
  • 'no direction either way' → the placements did not separate the two positions. Look at the precision line before concluding anything: if it is large, this session measured a tired hand rather than a set of boxes, and rerunning under a different seed on a different day is the cheap answer.
  • 'the landings track their starting points' → a hand that stopped short of where the eye said. It does not tilt the residual, because the starts are spread evenly around the shipped box, but it widens every interval above and usually means the placements were made faster than they were judged. Above about a quarter, treat the whole session as suggestive and rerun.
  • A run of 'the box was the wrong size' is the same second finding the forced-choice session can produce, and it belongs in the same place: the boxes come from one printing and the ink from another, so a rectangle can be in the right place and still not close around its mark. The repair is a re-measurement, not a displacement, and nothing in this check addresses it.
  • One session is one hand. If the residual is going to move three hundred thousand rectangles, a second person under a different seed costs another twenty-five minutes — and two hands landing in the same place is a much stronger claim than one hand landing anywhere.

Record it

make record CHECK=placement-residual-by-hand RESULT='seed 23 · <n> placements over <pages> pages · nearer ours <pct> [<lo>–<hi>] · residual (<x>, <y>) units against a precision of <p>, clustered by page <clustered intervals> → <adopt as proposed|adopt with the residual applied|contradicts the forced choice|says nothing>, and say which pages it can speak for'

Then do what it tunes:

  • packages/etl/data/pages/word-boxes.pin.json — the residual is the number that changes what is recorded there, where the forced choice can only say whether to record anything at all.
  • packages/etl/scripts/probe-mark-ink.mjs — a residual larger than a hand's precision is a measured statement that the correction it computes is short, which is the only evidence that could justify changing what it measures against.
  • docs/design/mark-registration.md §⑦ and §⑩ ① — §⑦'s recommendation is provisional pending a magnitude, not just a preference.
  • packages/etl/scripts/lib/adjudication.mjs — a session whose precision swamps its residual tunes the starting radius and the number of repeated marks, not the conclusion about the boxes.
