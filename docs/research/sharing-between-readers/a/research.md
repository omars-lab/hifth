# How could one reader send their own marks to another? Raw findings (researcher A)

Researcher A's raw notes for the question the owner asked on 2026-11-08: "Can we make a web version where we can share files from one user with another / OAuth scope, etc.", "does it need a separate site?", and the reader's own data following them between the iPad and the Mac through iCloud.
The design that comes from these notes is [design.md](design.md).
Written 2026-11-08. No app code was changed. Researcher B worked on the same question separately; these notes did not read B's.

## Apple: iCloud sharing and the web library

| source | how seen | what it says that matters |
| --- | --- | --- |
| [Apple: CKShare](https://developer.apple.com/documentation/cloudkit/ckshare) (read as [its data](https://developer.apple.com/tutorials/data/documentation/cloudkit/ckshare.json)) | fetched | A share lets one or more records from the owner's **private** iCloud database be shared "with many participants". Records go in their own zone; the whole zone or a tree of records is shared. "CloudKit limits the number of participants in a share to 100, and **each participant must have an active iCloud account**." Participants with write permission can change or delete what is shared. Setting the share's public permission above "none" lets "anyone with the URL" take part. The app must declare `CKSharingSupported` so tapping the link opens the app. |
| [Apple: Sharing Core Data objects between iCloud users](https://developer.apple.com/documentation/coredata/sharing-core-data-objects-between-icloud-users) (read as data) | fetched | Apple's ready-made sync helper does sharing with the system share sheet; each share gets its own zone; the owner can change permissions and remove people; a participant can leave. When a participant stops, the shared copy is deleted from their device. Automatic share updates since iOS 16.4 / macOS 13.3. The sample needs iOS 17.4 / macOS 14.4. "Doesn't support cross-share relationships." |
| [Apple: CloudKit JS](https://developer.apple.com/documentation/cloudkitjs) (read as data) | fetched | A JavaScript library so a web page can reach "the same public and private databases" as the Apple app. Needs web services turned on in the iCloud dashboard with a web token. The page does not say whether it is retired, and does not list browsers. |
| [Apple archive: Setting up web services](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/SettingUpWebServices.html) | fetched | The web sign-in lasts 30 minutes by default; two weeks if the reader ticks "Keep me signed in". The web token can be limited to named sites. |
| [Apple forum 839408 (July 2026)](https://developer.apple.com/forums/thread/839408) | fetched | A developer sharing sensitive data with a recipient "who may not have an Apple device", through the web library and Sign in with Apple. Says encrypted fields are not readable from the web library; asks how to expire a share on the server. **0 replies.** |
| [Apple forum 841292 (August 2026)](https://developer.apple.com/forums/thread/841292) | fetched | Web sign-in succeeds, the very first request is refused ("authentication required"), in Edge and Safari; the native app works with the same account. **0 replies**, a bug report filed. |
| [Apple forum 850775 (autumn 2026)](https://developer.apple.com/forums/thread/850775) | fetched | Another web-library sign-in failure on one kind of request; an Apple engineer replied with a pointer, no fix recorded. |
| Search: a CloudKit share link opened in a browser by someone with no Apple device | snippet (several forum and Stack Overflow results) | Developers report a raw share link in desktop Safari, Chrome or Edge on Windows shows "iCloud has stopped responding", while it works from Mail and Messages on Apple devices; the usual answer is a landing page of one's own. **Not confirmed by Apple.** |
| [Apple: Supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains) (read as data) | fetched | The file that lets a web address open the app must sit at `https://<host>/.well-known/apple-app-site-association`, over HTTPS, "with no redirects"; each sub-address needs its own file. |

## Signing in, and what each sign-in lets the app see

| source | how seen | what it says that matters |
| --- | --- | --- |
| [Apple: Authenticating users with Sign in with Apple](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple) (read as data) | fetched | The app may ask for the name and the email address. They are given "the first time the user logs in"; after that only the email comes back, never the name again. The app gets a user identifier. |
| [Apple support: What is Sign in with Apple?](https://support.apple.com/en-us/102609) | fetched | "Apps and websites can ask only for your name and email address." "Sign in with Apple won't track or profile you." Hide My Email gives the app "a unique, random email address that forwards to your personal email". |
| [Apple support: How to use Sign in with Apple](https://support.apple.com/en-us/102379) | fetched | Works "on other platforms like Android or Windows" through an Apple-hosted web page; the reader still needs an Apple Account, and the first sign-in asks for a code from a trusted device or phone number. |
| Search: Sign in with Apple in Firefox on Windows | snippet ([Mozilla support question 1410053](https://support.mozilla.com/fr/questions/1410053)) | One user report that it did not work in Firefox on Windows 11. A single report, not checked. |
| [Google: OAuth 2.0 scopes](https://developers.google.com/identity/protocols/oauth2/scopes) | fetched | `openid`: "Associate you with your personal info on Google." `email`: "See your primary Google Account email address." `profile`: "See your personal info, including any personal info you've made publicly available." `drive.file`: "See, edit, create, and delete only the specific Google Drive files you use with this app." |
| Search: are `openid email profile` exempt from Google's app review | snippet (third-party guides) | Sign-in-only scopes are "non-sensitive" and need no review; asking for any other scope can. **Not checked on Google's own page.** |
| [Google: security changes to the sign-in page (2021)](https://developers.googleblog.com/2021/06/upcoming-security-changes-to-googles-oauth-2.0-authorization-endpoint.html) | fetched | Google refuses sign-in inside an app's built-in web view ("disallowed_useragent"); an iOS app built on WKWebView "does not comply". **Hifth's iPad and Mac apps are exactly that**, so Google sign-in there has to be handed to the system browser or Apple's sign-in window. |
| [Supabase: Auth](https://supabase.com/docs/guides/auth) | fetched | Email and password, a link or a one-time code by email, about 19 outside sign-ins including Apple and Google. "The Auth Token scopes database access on a row-by-row level when used along with RLS policies." |
| [Supabase: Passkeys](https://supabase.com/docs/guides/auth/passkeys) | fetched | "Passkey support is experimental. The API may change without notice." A passkey is tied to one named domain, and "changing it later makes existing passkeys unusable"; sub-addresses of that domain may share it. |
| [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security) | fetched | A rule "adding a WHERE clause to every query", e.g. a row is readable only when its owner is the signed-in person. "A table in an exposed schema without RLS is readable and writable by any role with a grant on it" — including the public key every browser holds. |
| [Supabase: Pricing](https://supabase.com/pricing) | fetched | Free: 50,000 monthly signed-in users, 500 MB database. "Free projects are paused after 1 week of inactivity." Pro "from $25/month". |
| [Quran Foundation: OAuth2 scopes](https://api-docs.quran.foundation/docs/user_related_apis_versioned/scopes) | fetched | The closest outside example of a Qur'an app asking a reader's leave in pieces: separate permissions for bookmarks, collections, notes (including `note.publish`), reading sessions, activity days, goals, streaks, preferences, a `sync` permission, and social ones (`user.follow`, `user.followers.read`, rooms). "The user must consent to grant access to the scopes your app is requesting." |

## Where the data sits, and who can read it on the way

| source | how seen | what it says that matters |
| --- | --- | --- |
| [Excalidraw: end-to-end encryption](https://plus.excalidraw.com/blog/end-to-end-encryption) | fetched | The drawing is locked on the sender's device; only the locked copy is uploaded; the key is put in the link after `#`. "Anything that's added after the `#` doesn't get sent to the server, but is readable from the client-side JavaScript code." The server can store the copy and cannot read it. |
| [MDN: Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy) | fetched | A site is its scheme, host and port; the path is not part of it. "Each origin gets its own separate storage, and JavaScript in one origin cannot read from or write to the storage belonging to another origin." So everything under `blog.bytesofpurpose.com` shares one store. Cookies use a looser rule still. |
| [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) | fetched | "Shouldn't be used for sensitive transactions like sending passwords or credit card numbers." Not for running an online business or a paid service. |
| [GitHub Pages: about](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages) | fetched | Static files only. |
| [WebKit: full third-party cookie blocking and more (2020)](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) | fetched | Safari deletes a site's stored data "after seven days of Safari use without user interaction on the site"; a web app added to the Home Screen keeps its own count and is not expected to lose its data. |

## What I did not look at

- Whether CloudKit's web library works in Firefox today. No source for or against; the two 2026 failure threads are in Edge and Safari.
- Hosting a shared copy in the reader's own iCloud Drive or Google Drive and sharing that file's link. Plausible; not researched.
- The App Store's rules on sign-in (whether offering Google sign-in obliges offering Sign in with Apple too). Not looked at.
- Any Quran or hifz app with a working teacher dashboard, beyond the Tarteel Academy snippet.
- Prices or limits of Cloudflare's own small database and storage, which would be the alternative to Supabase on the host we already have ready.
