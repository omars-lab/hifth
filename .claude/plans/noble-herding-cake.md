# Plan: Hifth as a Mac app and an iPad app

## Context

Hifth is a static web app (React + Vite, hash-routed, relative paths, offline-ready) served
from `blog.bytesofpurpose.com/hifth/`. The near-term goal in `CLAUDE.md` is a private demo
that makes The Study Quran team lean in. A mus'haf on an iPad, and a Mac window with a real
menu bar, feel like a product in a way a browser tab does not. The owner also wants a few
outside testers (the Study Quran people) to install it themselves, via TestFlight.

Decisions already taken with the owner (2026-09-29):

- **Shell:** a thin SwiftUI app hosting a `WKWebView`, generated with XcodeGen, one source
  folder feeding an iPad-first iOS target and a native macOS target. Same shape as the
  sibling repos `../chips` (iOS + macOS targets, Makefile + scripts) and `../prayer-buddy`
  (deep-link enum that also reads launch env vars, launch-into-a-state-and-screenshot skill).
  Not Capacitor (no native Mac), not Tauri (weak iPad).
- **Distribution:** dev-signed installs on the owner's own Mac and iPad first; TestFlight for
  a few named outside testers second. TestFlight needs a paid Apple Developer membership
  and reopens the licence question in `docs/design/track-b-native.md` (GPL data inside an
  Apple-distributed binary). That question is carried as a decision record and is a gate
  before the first upload, not a reason to stop building.
- **Skills:** copy prayer-buddy's own `verify`, `deploy-device`, `troubleshoot` skills into
  `.claude/skills/` reworked for hifth; import a reworked subset of `swiftui-pro`
  (twostraws) and `rshankras/claude-code-apple-skills` per the review in §Skills below. No
  global marketplace installs.

What the web app already gives us for free (verified in this session):

- `base: "./"` and `import.meta.env.BASE_URL` everywhere: the bundle runs from any origin.
- The hash grammar in `packages/core/src/router.ts` (`#/<edition>/<target>?k=v`, e.g.
  `#/hafs-kfqc/2:255`, `#/hafs-kfqc/p45`, `#/hafs-kfqc/2:47-2:48`) **is** the deep-link
  language. A `hifth://` URL carries it verbatim; the shell adds no route grammar.
- `useHashRouter` restores once its resolver is ready and listens to `hashchange`, so setting
  `location.hash` from Swift is a normal navigation.
- The private pitch build already exists as a build, not only a dev server:
  `VITE_PITCH=1 vite build` keeps `dist/assets/private/` (`dropPrivateUnlessPitch` in
  `apps/web/vite.config.ts`). The public deploy workflow is untouched by anything here.
- Desktop spread, trackpad pinch (ctrl+wheel), touch gestures, safe areas, offline packs:
  all in the web app. The shell hosts; it does not re-implement.

Known things the shell must fix or switch off (from the survey):

- `ShareSheet.tsx:38` builds links from `window.location.origin`: inside the shell that is
  a local origin, so every shared link would be dead. The shell tells the page its public
  origin.
- `src/pwa.ts` registers a service worker and shows an install prompt: both skipped in-shell.
- Manifest says `orientation: portrait`; the native Info.plist decides on iPad and allows
  landscape for the two-page spread.
- Local machine: Xcode 26.6 and xcodegen present; iOS 26 simulator runtime is listed as
  Unavailable (needs `xcodebuild -downloadPlatform iOS`); one "Apple Development" identity,
  no distribution certificate, no provisioning profiles yet.

## Steps

### 0. Set up (one-time, this Mac)

1. `xcodebuild -downloadPlatform iOS` (several GB; needed for an iPad simulator on Xcode 26.6),
   then create an iPad simulator (`xcrun simctl create "iPad Pro 13" <devicetype> <runtime>`).
2. Confirm at developer.apple.com whether team `8BCAN49S59` is a paid membership. Free: device
   installs only, 7-day expiry, no TestFlight. Paid: TestFlight possible in phase 4.
3. Add permission allowlist entries to `.claude/settings.local.json` like chips and
   prayer-buddy do (`make:*`, `xcodebuild:*`, `xcrun simctl:*`, `xcrun devicectl:*`,
   `xcodegen generate:*`).
4. `pnpm exec playwright install webkit` so the `iphone` project and the new `ipad` project
   run locally.

### 1. Throwaway POC spike (the instrument that finds the options; ≤1 day)

Per the "rough build discovers what a list cannot" tenet. Commit a checkpoint first. Prove:

- Mac window shows the built app from the bundle; trackpad pinch zooms the page the way the
  web app already expects; keyboard shortcuts work.
- iPad simulator shows it; touch page turns and pinch work; landscape gives the spread; no
  double-tap zoom, no rubber-band, no link preview.
- Cold-start deep link: `xcrun simctl launch` with `SIMCTL_CHILD_HIFTH_ROUTE=/hafs-kfqc/2:255`
  opens on that verse; `open "hifth:///hafs-kfqc/p45"` on the Mac turns to that page while
  running and when not yet running.
- The pitch build's commentary panel loads its JSON from the bundle.
- Bundle served through the `hifth-app` scheme handler (settled below; `file://` is a
  known dead end, not an option to try).
- Probe from Web Inspector on day one: `isSecureContext`, `typeof caches`,
  `typeof navigator.share`, and that `gesturechange` fires on a Mac pinch.

Order that keeps the loop fastest: web-side change set with its tests → `native/` scaffold
→ Mac first (ad-hoc, run the binary with the env var) → iPad simulator → tests → device.

Output: `docs/design/native-shell.md` with what was felt, and the pros/cons written afterwards.
Losers deleted.

### 2. Real shell (graduate the POC)

1. `native/project.yml`: two app targets from one source folder (`TARGETED_DEVICE_FAMILY "1,2"`
   on iOS, `SUPPORTS_MACCATALYST: NO`), Debug builds unsigned on Mac (`CODE_SIGN_IDENTITY "-"`),
   `CODE_SIGNING_ALLOWED=NO` for simulator builds, `DEVELOPMENT_TEAM` passed on the command
   line from the certificate as prayer-buddy does. Copy `WebBundle/` as a folder reference.
2. `Route.swift`: one enum with `parse(URL)` and `fromEnvironment()` producing the hash
   string, mirroring prayer-buddy's `DeepLink.swift`. Rejects anything that is not
   `/<edition>/<target>[?query]`. Unit tests first.
3. `WebHost.swift` + `LocalScheme.swift` + `Bridge.swift`: the webview, the local serving
   choice from the POC, the three bridge messages (`ready`, `share`, `openExternal`), a
   document-start script that sets `window.__HIFTH_NATIVE__ = { platform, publicOrigin }`.
   Navigation policy: same-bundle links stay in; anything else opens in Safari.
4. `HifthApp.swift`: `.onOpenURL` → `Route.parse` → queued until `ready`, then
   `evaluateJavaScript("location.hash = …")`. Initial load uses `index.html#<route>` when a
   launch route exists (no timing race). macOS: window title "Hifth", minimum size that
   clears the desktop breakpoint (1024×740), Cmd+←/→ menu items forwarding to the page.
   iPad: all orientations, `viewport-fit=cover` honoured, safe area ignored by the view.
5. `apps/web/src/native-bridge.ts` + small edits: `pwa.ts` skips SW and install prompt when
   native; `ShareSheet.tsx` uses `publicOrigin` when present and routes `navigator.share`
   through the bridge; external links go through `openExternal`. Vitest for the origin choice
   and the skip.
6. Icon: reuse chips' `logo-from-png` pipeline (`scripts/update-appicon-contents.py`) with the
   existing hifth logo asset.

## Design points settled by the review (do these, do not re-derive)

Serving the bundle:
- **Custom scheme handler, not `file://`.** `loadFileURL` renders HTML/JS/CSS but WebKit
  refuses `fetch()` of `file:` URLs, and every page SVG is loaded with `fetch()`, so the app
  boots to an empty stage. Register `WKURLSchemeHandler` for `hifth-app`, document URL
  `hifth-app://app/index.html`; then `./assets/...` resolves same-origin and `BASE_URL`
  needs no change. Freeze `hifth-app://app` forever: it is the storage origin.
- Handler rules: right `Content-Type` per extension (`text/javascript` or the module script
  is refused), `Content-Length`, `/` and `/index.html` both serve index, real 404 responses,
  canonicalise the path and refuse anything outside `WebBundle/`, implement `stop` and never
  answer a stopped task (that is an uncatchable ObjC exception). Raw files, no gzip.
- Day-one probe from the page: `isSecureContext`, `typeof caches`, `typeof navigator.share`.
  Both degrade gracefully in the web app; the native share bridge is the fallback.
- Default `WKWebsiteDataStore`; localStorage/IndexedDB persist across launches and across
  `simctl install` (not `uninstall`). Changing bundle id, scheme, host, or Mac sandboxing
  later moves the data.

Mac:
- `allowsMagnification` stays **false**. WebKit then forwards trackpad pinch as
  `gesturestart/gesturechange` events, and `PageStage.tsx` already binds those through
  `useGesture` (its `target:` option makes the pinch device `gesture` on WebKit). The
  ctrl+wheel comment in that file describes Chrome/Firefox, not WebKit. No `magnify` bridge.
- `.defaultSize(1280×860)` so the desktop breakpoint (1024×740) is met on first launch;
  clear the WebKit context menu; `isInspectable = true`.
- Ad-hoc signing (`CODE_SIGN_IDENTITY="-"`) is enough locally. A copy sent to another Mac
  hits Gatekeeper on macOS 15+ (`xattr -cr` or "Open Anyway"); notarising needs a paid
  Developer ID.

iPad:
- Viewport `user-scalable=no, maximum-scale=1` in the native build (WKWebView honours it,
  Safari does not); also disable `scrollView.pinchGestureRecognizer` after `didFinish`.
- `scrollView.bounces = false`, `contentInsetAdjustmentBehavior = .never`,
  `allowsLinkPreview = false`, `-webkit-touch-callout: none` scoped to the stage, keep
  `allowsBackForwardNavigationGestures` off. No native gesture recognisers on the web view.
- `.ignoresSafeArea()` on the representable **plus** the `.never` above, or the top inset
  is applied twice. `viewport-fit=cover` is already in `index.html`.
- `allowsInlineMediaPlayback = true`, `mediaTypesRequiringUserActionForPlayback = []`, or the
  second verse's `new Audio()` refuses to play.
- Info.plist: `UISupportedInterfaceOrientations~ipad` all four, iPhone portrait only, **an
  `UILaunchScreen` dictionary** (without it iPadOS letterboxes the app and the desktop
  breakpoint never triggers), no `UIRequiresFullScreen` (deprecated on iOS 26; Split View
  and iPad mini landscape legitimately get the single-page layout).
- Deployment target 17.0 so the spike runs on the iOS 17.4 runtime already installed while
  the iOS 26 runtime downloads.

Deep links and timing:
- Cold start: put the route in the initial URL, `hifth-app://app/index.html#/hafs-kfqc/2:255`.
  Zero timing. Warm routes: queue until `didFinish`, then
  `callAsyncJavaScript("location.hash = route", arguments: ["route": hash])`, never a
  string-built `evaluateJavaScript`. Never load from `updateUIView`.
- One `RouteIntent` value fed by `.onOpenURL`, `HIFTH_ROUTE` env and launch args.
- Automation driver is the env var, not `simctl openurl` (that shows an "Open in Hifth?"
  alert once per install). `simctl launch` on a running app ignores env, so terminate first.
  Mac cold start for automation: run the binary directly with the env var; `lsregister -f`
  the built app so `open hifth://…` is deterministic.
- The web side posts `ready` (resolver ready) and every hash change; the shell mirrors the
  hash into a 1×1 native `Text` with accessibility id `hifth.route` (not `opacity(0)`) and
  into `document.title` → window title. That label is what screenshots and XCUITest wait on.

Screenshots: the app screenshots itself with `webView.takeSnapshot` when `HIFTH_SNAPSHOT_PATH`
is set, after `ready` plus a settle delay, then exits. Same on both platforms, headless, no
Screen Recording permission. `simctl io screenshot` and `screencapture -l` (window id via a
tiny `CGWindowListCopyWindowInfo` script; needs Screen Recording permission) stay as
with-chrome extras. Appearance from `HIFTH_APPEARANCE` (`overrideUserInterfaceStyle` /
`NSApp.appearance`); landscape from XCUITest's `XCUIDevice.shared.orientation`.

Bundle: XcodeGen folder reference `sources: [{path: WebBundle, type: folder, buildPhase:
resources}]`; the folder must exist before `xcodegen generate`. Copy in the Makefile, never
an Xcode run-script phase (user-script sandboxing on Xcode 26 fights it). Signing hashes
2,866 files in seconds. `app-web WEB=public` refuses to copy `assets/private/**`.

## Traps the review caught (so the build does not re-find them)

1. `loadFileURL` "works" until the first page SVG fetch fails.
2. Module script served without `text/javascript`.
3. Answering a stopped scheme task on a fast page turn: crash.
4. Turning `allowsMagnification` on "so pinch works": it eats the pinch instead.
5. Bridging `NSMagnificationGestureRecognizer` into fake wheel events: unnecessary.
6. No `UILaunchScreen`: letterboxed iPad, no desktop layout.
7. `.ignoresSafeArea()` without `.never` inset behaviour: double top inset.
8. Forgetting the media playback setting: audio needs a tap per verse.
9. String-built `evaluateJavaScript` with the route: quoting and injection bugs.
10. Route applied from `updateUIView` or before commit: page reload or lost in `about:blank`.
11. `simctl openurl` for cold start: blocked by the confirmation alert.
12. Copying the web build in a run-script phase: sandboxing errors.
13. Gzip plus `Content-Encoding` through the handler: not inflated.
14. Blank `screencapture` without Screen Recording permission.
15. Share links reading `hifth-app://app` in a pitch screenshot.
16. No iPad simulator device created; iOS 17.4 behaviour mistaken for iOS 26.

## Automated tests for iOS: what "Playwright-like" means here

Playwright drives browsers, not native apps, so it cannot launch the shell. But the shell
hosts WebKit, the same engine Playwright's `webkit` browser is, so the tests split cleanly:

| layer | what it proves | tool | runs where |
| --- | --- | --- | --- |
| Web app on iPad-sized WebKit | page turns, pinch, spread in landscape, safe areas, the pitch panel, goldens | **Playwright**: a new `ipad` project (`devices["iPad Pro 11"]`, landscape + portrait, `hasTouch`) next to the existing `iphone` project, plus an `ipad-golden` set | headless, pre-push and CI, seconds |
| Native shell on the simulator | cold-start route, `hifth://` while running, rotation, dark mode, no double-tap zoom, share bridge, screenshot of the real app | **XCUITest** (Apple's end-to-end framework: launches the real app, taps, swipes, rotates, reads the accessibility tree, attaches screenshots) | `make app-test`, simulator, ~1–2 min |
| Shell goldens | the real app's screen matches a baseline per route and orientation | XCUITest screenshots (or `app-shot`) compared with a pixel diff against `native/shots/baseline/`; `make app-golden` / `app-golden-update` mirroring the web `golden` targets | simulator, local |
| Pure logic | route parsing, scheme handler paths, MIME table | Swift Testing | `swift test`, seconds |

What XCUITest can and cannot do compared with Playwright: it taps and swipes the web content
through the accessibility tree (`app.webViews.staticTexts[...]`) but that is slow and flaky, so
shell tests assert on native mirrors the bridge maintains (the `hifth.route` label, the
window title) and leave in-page behaviour to Playwright. It cannot run JavaScript in the page.
Appium would give a Playwright-shaped JS API over the simulator but adds a heavy
WebDriverAgent setup for nothing the two layers above do not cover; not planned.

Decided with the owner (2026-09-29): all four layers, including shell goldens. One
prerequisite: Playwright's WebKit browser is not installed on this Mac (the `iphone` project
cannot launch locally today), so step 0 gains `pnpm exec playwright install webkit`, which
also makes the existing `iphone` project runnable in pre-push.

Where they land in the steps: the Playwright `ipad` project and its goldens are part of
step 2 (they test the web app and need no shell); XCUITest smoke is step 2 item 4's test;
`app-golden` / `app-golden-update` are step 3 targets with baselines under
`native/shots/baseline/` and the same "show the diff, ask, then update" recipe as the web
goldens.
